# 思考题参考答案

本文件汇总全书十章思考题的参考答案提纲。思考题多为开放性问题，答案不唯一。参考答案由 AI 生成，经人工略作审校，仅供读者参考。建议读者使用 LLM 结合书稿内容进一步讨论这些问题。

## 第一章 AI Agent 入门

**1. (★★) 如果你只能给一个 Agent 系统增加一项能力——更强的模型、更丰富的上下文、还是更多的工具——你会选哪个？在什么条件下你的选择会改变？**

> 对应“大脑/眼睛/手脚”公式，先找短板：通常优先补上下文，即补充观察空间（observation space）。若任务超出模型推理能力，换更强模型。若动作空间不足（例如无法访问公司内部系统），加工具。判断依据是分析失败轨迹，定位瓶颈在感知、决策还是行动。

**2. (★★★) ReAct 循环中，累计缓存读取量随轮数近似二次方增长。如何降低这种增长？**

> 第 i 轮读取的缓存前缀长度约与 i 成正比，累计读取量为 1 + 2 + ... + n = O(n²)；这里二次增长的是累计缓存读取费用，而非轨迹长度或 KV Cache 占用。可在达到 token 阈值时批量压缩早期轨迹，只保留结论与关键状态，并把大块中间结果外置后按需检索，或用子 Agent 隔离。不能每轮压缩，否则既可能损害 Agent 性能，也会引入额外的压缩调用和缓存重建开销。

**3. (★★) “模型即 Agent” 范式意味着模型在工具调用决策上越来越自主。但本章论证了 Harness 工程的重要性反而在增加。这两个趋势如何共存？Agent 框架未来的核心价值体现在哪些方面？**

> 马与缰绳隐喻：模型越强、自主空间越大，出错影响面越大，越需约束、验证、纠正。框架价值从“编排 LLM 调用”转向 Harness 五要素中的保障层：权限分类、熔断器、错误恢复、上下文压缩、工具生态。

**4. (★★) 消融实验中 “工具结果反馈” 的缺失导致 Agent 陷入无限循环。在生产环境中，除了工具结果缺失，还有哪些情况可能导致 Agent 无限循环？你会设计怎样的检测和终止机制？**

> 其他诱因：工具反复报同一错误、模型因幻觉调用不存在的工具、上下文压缩导致关键状态丢失、思考过程被剥离导致模型 API 报错、任务本身无解。机制：设定最大迭代次数等停止条件；检测重复调用（相同工具+参数指纹）；超过失败阈值后升级为人工干预。

**5. (★) 本章用感知、行动、策略三个维度分析了五个 Agent 产品。请选择一个你日常使用的 AI 产品，用这三个维度进行分析，并思考它的架构设计是否合理。如果由你来设计这个 AI 产品，有哪些改进空间？**

> 开放题。要点：仿照章中表格，写出眼睛（能看到什么信息源）、手脚（动作空间是否开放式、能否内部思考）、策略（Agent 执行循环的模式）。

**6. (★★) 如果你要设计一个专门处理航班订票的客服系统，你会选择工作流模式还是自主 Agent 模式？有没有可能在同一个系统中混合使用两种模式？**

> 主体采用工作流：身份核实→搜索→付款→预订四个节点，保证“付款前不能预订”等合规顺序，且把提示注入攻击面限制在单个节点内。开放性环节（理解需求、改签、航班取消后的替代方案推荐）切换为自主 Agent。高风险操作（大额付款、退款）需加人工确认。

**7. (★★★) 护栏部分提到了工具风险评级。如果一个工具在大多数情况下是低风险的，但在特定参数组合下变为高风险（如 `delete_file` 删除普通文件 vs 删除系统文件），你会如何设计动态风险评估？**

> 评级对象从“工具”细化到“工具+参数”：调用时根据可逆性、权限和影响面计算风险。采用基于规则的确定性检查（路径黑白名单、正则），而非模型判断。验证时应只检查结构化数据，防止提示注入操纵判断结果。

**8. (★★) 本章的 Agent 产品表格中，所有 Agent 的动作空间都是 “开放式” 的。一个受限的动作空间（比如只能从预定义选项中选择）在什么场景下反而优于开放式？**

> 高合规、高风险、错误不可逆场景：如退款、付款，受限选项即“约束”，天然防呆，从设计上让错误无法发生。

**9. (★★) 人工干预机制要求 Agent 能 “优雅地移交控制”。但在实践中，用户可能不在线、响应很慢、或者给出模糊的指令。此时 Agent 应该怎么办？**

> Fail-safe：高风险操作在未获确认时暂停，而非默认执行；先完成可逆的低风险部分，将高风险部分记录在文档中，便于人类决策和 Agent 恢复；使用异步沟通工具（消息、邮件）通知用户并设置超时策略；指令模糊时先澄清意图。

**10. (★★★) 引言指出 “好的设计原则应该穿越模型的迭代周期”，但实现这些原则的具体工程手段可能会随模型能力进步而过时。试举一个这样的 Agent 工程手段，并说明理由。**

> 示例一：通过约束采样强制工具调用符合严格格式。这是在模型容易输出非法 JSON、遗漏参数时采用的可靠性补丁；随着模型的格式遵循能力提高，其收益可能逐渐降低，但高风险场景仍应保留确定性的格式校验。
>
> 示例二：为弥补模型无法持续吸收新知识而引入外部知识库。如果模型未来具备可靠的持续学习能力，一部分知识维护可能从模型外部迁移到参数中。不过，外部知识库在实时更新、精确检索、权限控制和来源追溯方面仍有独立价值，因此更可能缩小适用范围，而非完全消失。
>
> 示例三：要求所有能力都必须通过模型 API 的标准工具调用接口暴露，禁止自定义调用形式。Skills 已经展示了另一条路径：用文本描述能力及操作方法，再让模型通过通用命令行工具执行；从模型视角看，这相当于在通用执行器之上理解并遵循一种自定义的文本调用协议。随着模型理解任意接口的能力增强，“必须使用标准工具调用格式”不再适合作为普遍原则。标准格式对于互操作、结构化校验以及能力较弱的模型仍然有用，但它应是基于场景的工程选择。
>
> 示例四：要求提示词与全部工具定义必须预先放在上下文开头。这种做法源于早期模型的指令遵循能力有限，提示或工具定义离开熟悉的固定位置后，模型往往难以正确识别和执行。Skills 会在运行过程中按需把提示词加载到上下文中间；动态工具发现也会在找到新工具后，把工具定义追加到已有轨迹之后。随着模型的指令遵循能力增强，以及针对这类动态加载方式进行专门的后训练，提示词和工具定义不再必须固定在上下文开头。

## 第二章 上下文工程

**1. (★★★) 实验 2-3 中，滑动窗口配置未在轮次上限内生成最终回复。请结合轨迹分析哪些信息被移除，并设计一种保留关键状态、控制历史长度的方案，说明它对前缀缓存的影响。**

> 先对照被移除的消息，检查目标、已读文件、失败原因和未完成调用是否丢失。可将这些信息整理为阶段摘要，保留最近的调用与结果对，并将大输出归档后提供索引。替换历史会从修改点起影响缓存；稳定的系统指令与工具定义仍可复用。子 Agent 隔离可减少进入主历史的探索材料。

**2. (★★) Qwen3 的 Chat Template 按最后一个真实用户查询的位置处理历史思考。若一次 ReAct 循环持续上百轮，你会如何管理逐渐增长的推理内容？请比较历史思考的裁剪、回传与前缀绑定协议，并说明 Harness 应如何适配。**

> 先按模型与接口协议决定哪些推理内容必须回传，再设置历史预算。允许裁剪的协议可保留近期推理，并把长期计划整理为状态摘要；要求回传的接口应保存原始响应字段。若 thinking 与前缀绑定，改写前缀后需按协议处理受影响的推理块，或使用服务端压缩。比较方案时同时检查任务连续性、重复调用、输入量和缓存命中。

**3. (★★) 假设要把约十五万字符的搜索材料压缩到两千字符，你会保留哪些事实、关系与来源？怎样检查摘要是否足以支持后续问题，又怎样恢复被省略的细节？**

> 保留人物、时间、机构、关系、关键证据与尚未解决的问题，并原样保存用于定位的标识符。为摘要设计后续查询，检查遗漏和歧义；将原始材料归档，保存来源、抓取时间及读取入口。链接帮助定位，原文快照支持长期复核。压缩比例由任务需要与质量检查共同决定。

**4. (★★) 工具计数器漏记了一次调用，状态栏因此给出错误的剩余次数。请设计事件记录、汇总校验和执行层检查，说明如何发现并修复这种不一致。**

> 为调用建立唯一事件 ID，记录请求、执行和返回状态，并明确次数上限统计尝试还是成功。通过幂等更新避免重记，通过事件重放和定期对账发现漏记。执行层根据可信计数检查权限，模型读取状态用于规划。发生不一致时保留事件记录，重建汇总后再继续；来源不明的文本应作为待核实材料处理。

**5. (★★) 实验 2-4 比较了语气、信息组织与工具描述。若系统提示词由多人长期维护，你会如何管理版本、检查规则冲突，并用回归任务评估每次修改？**

> 将提示词纳入版本管理与评审，由业务、运营和工程人员共同检查流程与边界。维护典型任务、边界案例及已知失败的回归集，每次修改记录目标和结果。使用 Markdown/XML 组织规则，检查重复与冲突；稳定规则放在可复用前部，动态状态按消息追加，专项流程可拆成 Skills。

**6. (★★★) 宠物店案例同时包含单条检索与总体统计。请设计原始记录、统计摘要和查询路由，使系统能高效回答这两类问题，并说明摘要需要在什么时候更新。**

> 逐笼记录按笼号索引，颜色总数由程序根据新增、移除和变更事件增量维护。单笼查询读取对应记录，数量查询读取统计摘要，涉及新维度的问题回查原始数据。定期重算总数与增量状态对账。跨会话需要保留这些状态时，将记录与索引持久化，并在新任务中按需加载。

**7. (★★★) 一个 Skill 已在目录中，但模型没有发现它适用于当前任务。你会如何从描述、目录组织、显式触发和评估样例四个方面排查问题？**

> 检查 Skill 名称和描述是否覆盖真实任务表达，补上具体触发条件与容易混淆的边界。目录较大时可按任务检索候选项。显式触发提供直接加载路径；评估集同时包含应该触发、不应触发及描述相近的案例，分别统计漏选和误选。

**8. (★★) Skill 已经成功加载，模型却漏掉了其中的验证步骤。请设计一个对照实验，区分触发、理解、工具使用和完成判断中的问题，并比较不同模型的表现。**

> 固定任务、工具和 Skill 版本，分别测试自主触发与显式加载。记录目录是否可见、正文是否读入、关键步骤是否理解、工具调用是否成功以及验证是否执行。不同模型使用各自支持的消息协议，在相同产物标准下比较。Skill 内容追加后保持原位，后续消息继续追加，可以保留相应前缀的复用条件。

**9. (★★★) 系统包含大量工具，工具集合又经常变化。你会如何安排固定定义、工具目录、按需加载结果与运行时状态的位置？请同时考虑发现准确率、上下文预算和缓存命中。**

> 将高频稳定工具放在前部并固定顺序，用目录和工具搜索按需提供其余定义。新增内容按接口支持的方式加载，避免无关变动扩散到已有前缀。动态状态放在后部，并选择替换或追加策略。父子 Agent 可复用共同的稳定指令；各自的权限和任务差异应明确表达。通过发现成功率、工具调用正确率、输入量和实际缓存指标共同评估布局。

## 第三章 用户记忆和知识库

**1. ★★ 用户在两次会话中提供了不同的家庭住址。请设计记录结构与更新流程，区分搬家、更正、临时住处和信息冲突，并说明当前查询与历史查询分别如何取用。**

> 记录地址、用途、生效时间、来源会话和状态。用户明确说明搬家时，新增当前住址并结束旧住址的有效区间；更正笔误时保留修订依据；临时住处增加适用期限。对象或时间尚不清楚时，保存冲突并向用户确认。当前查询选择有效记录，历史查询按目标日期读取，原始表达用于回查。

**2. ★★ 原始文档包含矛盾信息时，上下文前缀可能把错误一起写入索引。你会怎样保存来源、版本和不确定项，并在检索与生成阶段使用这些信息？**

> 前缀与原文分别保存，标明生成版本和引用范围。来源、发布时间、适用时间和权限进入元数据，矛盾条目保留关联。检索先执行权限与时间过滤，再综合相关性和来源质量排序；生成时对冲突材料并列说明，并回查原文。可用带否定、时间变化和错误来源的用例检查前缀是否引入新断言。

**3. ★★ 将图表转换为文本后，哪些空间关系容易丢失？请用表格、架构图或折线图举例，设计原图、结构化表示和文本索引协同检索的方案。**

> 例如，表格中的合并表头决定一个数值属于哪个年份和地区。仅保存“收入100”会丢失这组关系。可以同时保存原图、页码与区域坐标，以及包含行表头、列表头、数值和单位的结构化单元格。文本索引用于定位，回答时读取结构化记录，遇到歧义再查看原图；架构图还应保留节点、连接方向和包含关系。

**4. ★★★ 随着模型和长上下文能力提升，分块、索引和检索流程中的哪些工作可能交给模型？请结合 Rich Sutton“苦涩的教训”中对搜索和学习的讨论分析，并设计实验比较全量输入与按需检索，同时检查任务质量、计算成本和权限约束。**

> 模型可能承担分块边界选择、查询改写和结果整合。比较时固定资料、问题与模型，分别运行全量输入、单次检索和多轮检索，并随资料规模增长测量质量、延迟和费用。加入跨文档统计、精确条款、更新事实和权限差异等任务，检查方法在哪些条件下仍有效。统计可以交给可验证的聚合计算，权限则由输入构造和执行层强制实施。

**5. ★★★ 如果模型已经掌握大量领域知识，外部知识库还应保存什么？请分别讨论公开常识、持续更新的规则、私有资料和需要精确追溯的证据。**

> 稳定公开知识可以主要依靠模型，但最新规则需要版本和生效范围，私有资料需要访问控制，精确论证需要来源与原文。外部知识库还支持更正、删除和审计。采用参数化记忆时，也要验证更新隔离、事实回忆与推理能力，并为需要追溯的内容保留证据记录。

**6. ★ RAPTOR 的多层摘要与 GraphRAG 的实体关系、社区摘要分别支持哪些查询？请为总体概览、局部细节和多跳关联各举一例，并说明需要检查什么证据。**

> RAPTOR 的高层摘要适合总体概览，底层材料支持细节，查询可以跨层选择。GraphRAG 的局部实体关系支持“用户—医生—医院—地址”等关联查询，社区摘要支持主题概括。总体概览检查覆盖范围，局部细节检查原文，关系问题检查每条边的对象、方向、时间和来源；实体合并错误也会影响后续路径。

**7. ★★ 目录、链接与向量索引如何协同组织知识？请设计一个需要人和 Agent 共同维护的知识库，说明导航、语义搜索、版本更新与权限过滤各自的位置。**

> 目录按业务主题和权限组织，入口页概括内容，链接连接经常一起使用的条目；向量与关键词索引帮助发现尚未知道位置的材料。人或 Agent 提交知识变更后，更新链接与摘要，再重建受影响索引。读取原文和派生内容都执行调用者权限过滤。用已知位置导航、模糊查询和跨主题问题分别评估这套结构。

**8. ★★★ 从案例中提取字段并聚类后，怎样判断原型有用？请区分聚类特征的重要性、结果预测能力与因果解释，并设计留出评估和专家复核流程。**

> 先检查字段提取是否准确、缺失处理是否一致，再看簇内共同特征、簇间差异和重复采样的稳定性。区分簇的特征权重描述分组结构；预测能力需要在留出样本上评价；因果解释还需要控制混杂、选择合适设计及领域证据。专家可以检查字段定义、原型描述和例外，评估时还应核对统计数字及样本覆盖范围。

**9. ★★★ 为 Markdown 用户记忆库设计增量更新与定期整理流程。若审核者与提议者使用相同模型，且审核者只能看到提议者挑选的片段，哪些错误容易遗漏？请从证据覆盖、工具权限和审核评估三个方面改进。**

> 增量流程由提议者检索旧知识、提交差异与来源，审核者独立回查，检查通过后合入并更新索引。定期整理按覆盖清单去重、合并、调整目录并核查原始材料，重组仍走同一审核流程，发布后回放检索任务。只看选定片段容易漏掉否定、时间变化和跨文件冲突；相同模型还可能重复相似误读。给审核者开放授权范围内的完整证据检索与检查工具，分别限制分支写入、审核和发布权限。用预先植入的错误变更评估发现率，比较不同模型组合与证据范围，并设置迭代预算和人工处理入口。

## 第四章 工具

**1. (★★) MCP 将工具接入与 Agent 框架分开。请选择流式结果、双向交互或长任务状态管理中的一种需求，说明它需要哪些协议能力、哪些宿主能力，并讨论接入现有 MCP 时需要补充的设计。**

> 以长任务为例，可以把“提交计算”和“获取结果”分开：提交后返回任务 ID，后续通过状态查询或通知获取进展。服务端需要保存任务状态与产物，约定排队、运行、完成、失败和取消的转换；宿主需要保存任务 ID，在断线后恢复查询，并把新结果送回正确的 Agent 任务。接入时还要检查所用 MCP 版本、扩展与客户端支持情况，再决定使用已有能力还是补充明确的业务工具。协议连接关闭、客户端停止等待、后台任务取消，是三个需要分别处理的状态。

**2. (★★) 多个 MCP 服务器提供相似工具时，应如何选择？以“一个返回摘要，另一个返回全文”为例，设计工具描述、来源标识和选择依据，让 Agent 能够利用这种差异。**

> 可以为工具保留服务器命名空间，用 `docs.summary` 与 `docs.read_full` 等名称区分用途。描述中说明覆盖的数据源、返回内容、分页方式、时效与成本。例如，摘要工具适合筛选候选文档，全文工具适合核对原文、引用段落和查找具体条件。模型先根据任务选择读取粒度，必要时从摘要继续读取全文。宿主则核对来源、版本和授权范围，固定名称到实际服务的映射，并用真实查询检查描述与返回值是否一致。

**3. (★★) 除了写入代码后运行检查，“执行—验证—反馈”还能用于哪些场景？请选择两个例子，说明验证方法、失败反馈及成本，并讨论何时适合立即验证、抽样验证或异步验证。**

> 第一个例子是修改配置：先检查格式与字段，再在隔离环境中启动服务，读取健康状态或行为结果。失败时返回出错字段、启动诊断和实际状态，帮助 Agent 判断应修改配置还是恢复原值。第二个例子是生成演示文稿：渲染页面，检查文字是否溢出、图表是否遮挡，并把页码和位置反馈给生成者。格式检查开销较低，可以立即执行；完整启动或逐页视觉检查开销较大，可以按变更范围、风险和耗时选择增量检查、抽样检查或异步检查。
>
> 外部操作也可以查询执行结果。例如，邮件提交后读取服务端消息状态，订单创建后按业务编号查询记录。应选择读取状态、回执或审计记录的验证接口，并区分“已接收”“已完成”等不同含义。涉及外部影响时，事前审批与事后验证各自承担相应职责。

**4. (★★) 面对数千个工具，除了主动发现，还可以怎样组织能力？结合分类目录、工作流模板或通用执行器，说明一种方案的适用条件与取舍。**

> 对重复度较高的业务，可以把常见任务整理成工作流模板。例如，资料汇总模板规定“搜索候选—读取正文—核对来源—生成报告”，每一步只提供相关工具。模板减少同时暴露的定义，也帮助模型理解步骤间的数据依赖，适合流程稳定、输入差异可控的任务。遇到新任务时，需要保留调整步骤或补充工具的入口。
>
> 还可以组合其他方法：按领域组织目录，常驻少量高频工具；将详细用法写入 Skill，按需读取；用通用代码执行器调用稳定的库或 API，减少专用接口数量。选择时应同时比较上下文开销、检索或阅读步骤、权限控制和执行可靠性。

## 第五章 Coding Agent 与通用 Agent

**1. (★★) 为一个需要读取项目文件、安装依赖和运行测试的 Coding Agent 设计沙盒。你会如何配置文件、网络、进程和资源权限？任务需要扩大权限时，怎样表达请求、检查范围并保留记录？**

> 先列出任务必需的访问：项目工作副本可写，参考资料只读，依赖通过批准的源获取。用独立执行环境限制进程、运行时间、内存和磁盘；凭证由受信任服务保管。扩大权限时说明目标资源、操作、期限与原因，由执行层检查并记录授权。用构建、测试和资源超限用例检验配置。

**2. (★★★) 创建者连续生成和修改多代 Agent 时，框架缺陷与领域错误可能逐步累积。如何用参考版本、回归测试、行为评估和回退机制追踪这种变化？**

> 给参考框架、每代产物及需求分别保存版本，记录生成来源和变更。回归集同时覆盖消息协议、工具关联、状态恢复和真实领域任务，并保留独立任务检查泛化。比较新旧版本的成功率、成本与失败类型，验证通过后发布；发生退化时恢复最近通过验收的版本。

**3. (★★) 日志格式变化可能来自正常升级，也可能来自生产者缺陷。自适应解析系统应保留哪些证据，依据哪些条件决定新增解析器、报告异常或暂停处理？**

> 保存原始日志、生产者版本、变更说明和旧解析器结果。先对照接口约定检查字段含义、类型与取值，再验证正常及异常样本。已确认的格式升级进入解析器迭代；含义冲突、数据缺失或无来源变更进入问题报告，必要时暂停相关处理。新解析器与告警记录可以同时保留。

**4. (★★) 提议者—审核者循环中，审核者认为页面信息密度合理，用户却觉得拥挤。如何把用户偏好转化为示例、评分条件和交互反馈，并检查后续修改是否符合要求？**

> 请用户标注可接受和过于拥挤的页面，形成字号、留白、信息密度等具体标准。审核反馈带页码和问题位置，修改后展示同一页面便于对照。偏好记录包含用户、任务和适用范围，后续任务按范围引用；抽样复核可以发现审核标准与用户体验的偏离。

**5. (★★) Coding Agent 可以更新知识库、架构文档和项目指令，也可以把操作序列固化为代码。如何识别冗余或过时的规则，为规则设计适用范围、验证方法和退出条件？从一次成功修改发展为第九章讨论的持续进化，还需要哪些积累与评估机制？**

> 每条规则记录来源、适用范围、验证用例及最近检查时间。重复规则合并，失效规则随版本归档，稳定且可判定的要求进入 Linter、测试或工具校验。先用历史任务验证规则变化，再检查新任务收益。持续进化还需要运行证据积累、候选修改、独立评估、发布与回退形成长期循环。

**6. (★) 对远程协作友好的团队通常也便于 Agent 获取工作信息。请检查一个熟悉项目的需求、架构、决策记录和验收标准，列出最需要补充的文档，并说明它们能帮助 Agent 完成哪些具体任务。**

> 可用新成员首次接手项目的过程自查：能否找到需求背景、架构关系、构建方法、测试入口和验收条件。优先补充影响当前任务的知识，例如解释一个模块的职责、记录一次技术取舍、提供可执行的验收用例。明确文档负责人和更新触发条件，使资料跟随代码维护。

**7. (★★★) 对同时访问私有数据、处理不受信任内容、进行外部通信并使用持久记忆的 Agent，如何安排身份授权、来源标记、数据流检查与记忆写入审核？请用一条正常业务流程说明这些检查的位置。**

> 以读取客户资料并发送服务通知为例：身份服务确定可访问客户，资料来源与外部网页分别标记，通信接口检查收件人和允许发送的字段。任务完成后，记忆写入检查来源、必要性、敏感程度及有效期。数据读取、对外发送和跨会话保存分别记录，便于复核异常及撤销失效授权。

**8. (★★) 在 SQL 与 HTML 的 Artifact 模式中，模型生成产物，执行服务处理查询或渲染，界面直接呈现结果。哪些信息适合再交给模型解释？如何检查查询权限、资源预算、页面隔离和展示结果的一致性？**

> 完整表格可由执行服务直接呈现，模型按需读取聚合结果、异常行和字段解释。查询使用受限账号与结构校验，限制可访问数据、函数和执行预算；页面在隔离环境中渲染，声明式组件仍检查属性与动作。用参考查询和页面值对照检查结果，再核对单位、日期与统计口径。

**9. (★★) 工具根据数据库中的业务状态校验规则，参数说明则帮助模型准备调用。请以取消预订为例，说明自然语言政策、参数例子、执行层校验和边界测试各自承担什么职责；政策变化后，哪些内容需要同步更新？**

> 自然语言政策帮助模型理解适用条件并向用户解释；参数例子展示日期和预订标识的具体格式。工具读取可信订单、身份和服务端时间，在执行前完成授权与规则校验，并处理并发变化。expected_* 字段可以表达模型预期，实际裁决依赖执行层读取的状态。政策更新时同步修改说明、实现、示例和边界测试，并检查旧预订的适用版本。

## 第六章 交互：观测与动作空间的扩展

**1. (★★) 异步 Agent 收到新事件时，需要判断它与当前任务的优先关系。如果这个判断涉及语义理解，例如识别用户是在补充条件还是要求立即停止，应如何分配规则引擎与 LLM 的职责？请比较响应时间、费用和误判后果。**

> 可以先按可信来源和事件类型设置规则：明确的停止信号、执行器故障和到期任务进入相应处理通道。自然语言中的意图由分类模型辅助识别，结果交给运行时按权限和当前状态调度。规则开销小、行为容易检查；模型能处理表达变化，但增加推理费用、延迟和误判概率。关键停止通道应能直接生效，并为分类超时或不确定结果规定处理方式。外部事件正文作为待分类数据，权限和优先级由可信元数据与调度策略约束。

**2. (★★) 事件队列积压了 20 个事件：10 个工具结果、5 条用户消息和5个系统提醒。你会如何组织它们的顺序、格式和处理状态，使模型能够追踪任务依赖并回应重要变化？**

> 先按任务标识、来源、时间和依赖关系归组，识别真正重复的事件；同一任务的条件更新按时间保留，工具结果与原始调用配对。需要立即处理的停止或故障事件由运行时优先接入，其余事件按任务组织成清单，标记未处理、处理中和已处理。长工具结果保留决策所需的事实与状态，完整内容放在可检索的外部存储中。每轮结束更新清单，避免已经消费的事件重复触发动作。用户新条件应与受到影响的计划或待完成任务关联。

**3. (★★★) Agent 可以使用专属邮箱和电话号码，也可以在授权后操作用户的个人账号。请结合后台运行、对方的身份核验要求、权限范围与审计，讨论两种身份方式各自适用的场景。**

> 独立身份适合预约、查询与日常沟通，便于区分 Agent 的活动并单独管理访问范围。涉及用户账户内的数据或业务操作时，可以采用范围明确、可撤销的授权，并在对方要求账户持有人确认时接入用户。例如，客服电话可以由 Agent 先说明需求，再通过三方通话完成本人确认；可视化登录可由用户在受控界面中完成。两种方式都应记录代理关系、授权范围与实际动作，权限隔离程度取决于具体账号和环境配置。

**4. (★★) 端到端语音模型直接处理音频，中间环节的错误较难从外部定位。如何设计观测与对照实验，区分感知错误、推理错误和表达错误？**

> 保存经过授权采集的输入音频、事件时间线、工具结果与输出音频，并记录模型可提供的文本输出。用同一段输入做直接音频回答和先转录再回答的对照，再加入人工核对的转录，观察错误是否随输入形式变化。数字听错后计算错误属于感知影响推理；输入数字正确但运算错误，需要检查推理；答案文字正确而播报遗漏，需要检查输出。另对语速、噪声、端点、插话和首段延迟分别评估。可读文本是诊断线索，其覆盖范围由模型提供的接口决定。

**5. (★) Step-Audio R1.1 的 MPS 让构思与表达协同推进。系统应如何使用停顿、进展说明和分段表达？后续推理改变了已说出的结论时，应怎样处理？**

> 表达节奏应服务于当前任务：需要等待查询时说明正在核对什么，解释复杂内容时分段并适当停顿。能够提前表达的内容包括已确认事实、任务理解和接下来的处理步骤；业务结论需要相应证据支持。若后续发现结论有误，应及时指出具体修正及其影响，并同步更新后续行动。评价时既检查首段响应和语音自然度，也检查结论一致性与实际完成情况，避免把填充词数量当成自然交流的目标。

**6. (★★) SoM 的视觉区域标注与 DOM 元素索引都为模型提供可引用的候选。遇到非标准控件、遮挡或动态变化时，如何组合重新标注、坐标预测和操作后检查？**

> 先检查候选是否因滚动、刷新或动态加载而过期，必要时重新获取页面状态并生成映射。结构化信息缺失时，可以通过截图补充视觉候选；目标清晰而候选未覆盖时，再使用坐标预测。执行前校验图像到桌面的坐标变换，执行后检查预期界面变化。若目标本身仍不清楚，可以放大区域或进一步读取界面信息。三条路线都需要应对遮挡与状态变化，并保存本次定位所依据的画面。

**7. (★★) 遥操作数据的质量受操作者技能影响。抖动、绕路、停顿和抓取失败会怎样影响 VLA 训练？如何筛选数据，同时保留有价值的失败恢复过程？**

> 模仿学习可能把频繁抖动和无效绕路学进动作策略。采集时可以记录成功状态、路径长度、速度与加速度变化、碰撞、越界、人工接管和观测缺失，用这些指标定位需要复核的片段。筛选还要考虑任务难度：成功恢复一次滑落可能比顺利完成更能补充训练覆盖。将稳定示范、失败动作和恢复过程分别标注，再按训练目标选择数据，既能提高基础动作质量，也能保留纠错经验。

**8. (★★★) 语音、Computer Use 和机器人都可以采用统一模型、模块化级联或前台交互与后台推理分工。面向未来五年，你倾向于怎样组合这些路线？请结合延迟、可观测性、升级成本与任务风险说明判断。**

> 可以先确定场景约束，再选择组合。连续语音需要维护听说时序，复杂业务分析需要较长推理，两者可以通过任务与状态接口协作。Computer Use 需要持续取得页面变化，机器人还要维持高频控制。模块化便于替换、定位问题和独立升级，代价是接口通信与状态一致性；统一训练有机会改善信息利用与时序协调，但升级和诊断需要更多整体评估。笔者倾向于保留可替换的后台推理能力，同时持续改进前台交互模型；这一判断可以用实际延迟、任务成功率和维护成本检验。

**9. (★★) 标准 Web 页面可以提供 DOM 或无障碍信息，Canvas、WebGL 与自绘控件往往依赖视觉定位。同时维护结构化与视觉两条路径，会增加哪些成本，又能获得哪些收益？**

> 结构化路径提供角色、标签和元素引用，便于理解表单与页面关系；视觉路径覆盖截图中可见但未暴露结构的内容。维护两者需要处理状态同步、元素与图像的对齐、不同失败类型以及额外测试。收益是能够按页面条件选择更合适的定位方式，并用截图检查结构化信息是否符合当前界面。可以用相同任务分别测量定位成功率、操作轮数、延迟和恢复成本，决定何时使用单一路线、何时组合。视觉模型能力增强后，也应重新评估结构化路径带来的实际收益。

**10. (★★) 动作分块让 VLA 一次生成一段未来动作。若执行期间物体被移动，怎样协调分块长度、重新观测、后台推理和动作中断，兼顾执行效率与响应速度？**

> 区分模型预测的动作长度与每次实际执行的长度：可以预测较长轨迹，只执行前一小段，再用新观测滚动更新。推理与执行重叠时，需要处理新旧动作块的衔接；环境变化较快或接近障碍物时，缩短执行片段并提高状态检查频率。控制层持续检测限位与异常，必要时按硬件要求减速或停止，并丢弃失效的剩余动作。选择参数时一起测量推理延迟、轨迹连续性和最坏响应时间，避免仅以吞吐决定动作长度。

**11. (★★★) 快速交互需要及时行动。请分别以语音回复、网页提交和机器人抓取为例，设计动作分级、状态确认与停止机制，使响应速度与任务后果相匹配。**

> 语音可以先确认收到任务，待查询完成后再表达业务结论；网页可以先读取或填写草稿，提交前检查对象、内容和授权；机器人可以先规划接近路径，在抓取前确认物体位置与工作区状态。动作是否允许执行，由权限、当前状态和所需确认共同决定。快慢模型都通过相同的执行约束，运行系统负责阻止条件未满足的动作。停止时分别处理生成与播放、尚未提交与已经提交的请求，以及运动指令与实际执行器状态。

**12. (★★★) 选择唤醒、安全点、取消、抢占或快慢分工中的一个原语，比较它在事件驱动任务与机器人动作分块中的实现。环境变化速度、动作可逆性和观测成本怎样影响设计？**

> 以取消为例，后台软件任务需要停止继续派发、向执行器发出取消请求、确认资源退出，并记录已经发生的外部效果。发出取消到真正停止之间的时间取决于工具和服务接口。机器人还需要让控制层在规定周期内响应，按动力学与硬件要求停止运动，再读取当前位置与物体状态。环境变化速度决定可接受的响应期限，可逆性决定停止前还需要哪些确认，观测成本与可获得性决定反馈频率。可以据此设置安全点与超时，同时为紧急事件保留直接通向执行层的停止通道。

## 第七章 Agent 的评估

**1. (★★) 评判模型可能偏好较长回答、特定文风或某个展示位置。怎样设计控制样本、交换测试和人工校准集，区分内容质量与这些偏好？**

> 先建立包含任务要求、参考依据和人工判定的校准集，再构造内容一致、长度或文风不同的回答。配对评判交换展示位置，记录胜负是否随位置变化。相关性分析用于发现线索，控制样本帮助区分长度与信息量的影响。按错误类型检查一致率和混淆情况，在 Rubric 中明确必要信息、简洁性与接受范围，并将分歧样本补充为判例。不同家族模型可以提供额外判断，人工保留集用于持续检查共同盲点。

**2. (★★★) 公开评估集可能进入训练数据。怎样组合新任务、参数化环境、保留集与生产样本，降低数据污染对结论的影响？canary 标记能够提供哪些线索？**

> 让评估同时包含定期更新的新任务、参数化实例、独立保留集与经过脱敏确认的生产案例。任务生成规则可以复用，评估实例与训练实例应分别管理，并在任务结构、时间和环境上保持足够差异。参数变化还应保留需要推理的关系，避免仅替换名称和数字。canary 标记可以帮助发现文本被复制或接触的线索，判断训练污染还需要结合数据来源、发布时间和行为证据。分别报告不同来源的成绩，有助于观察模型是否只熟悉某一类公开题。

**3. (★★) 根据专家指导、全面覆盖、重要性加权和自包含四项准则，为“回答有帮助”和“语气恰当”设计 Rubric。怎样用边界案例处理评价者的分歧？**

> 先定义受众与任务。“有帮助”可以拆成是否回应当前诉求、是否提供可执行下一步、是否保留必要条件；“语气恰当”可以拆成是否尊重用户、是否与沟通场景匹配、是否避免无依据承诺。每项给出档次、正反例和边界情况，例如投诉回复中简洁承认问题与冗长重复道歉的差异。请多位熟悉业务的人独立评分，讨论分歧背后的任务理解，再更新参考材料和判例。评分可以保留有意义的偏好差异，聚合方式按产品目标预先规定。

**4. (★★) τ²-bench 使用模型模拟用户。怎样检查模拟用户是否遵循任务设定，能否覆盖情绪、歧义和信息遗漏等真实交互条件？**

> 从遵循设定和代表真实交互两个层面检查。前者逐轮核对模拟器知道什么、可以透露什么、是否编造事实，以及是否正确响应 Agent 的提问；后者比较真实用户样本中的歧义、遗漏、情绪、纠正和中断。为这些条件建立场景矩阵，检查不同模拟策略下的任务成功率、轮数和错误类别。再用人工交互样本校准关键任务，观察绝对成绩和模型相对顺序是否随模拟器改变。

**5. (★★) Bradley–Terry 用一维潜在实力解释配对偏好。哪些任务分布或用户群体可能形成循环偏好？怎样利用分组分析与模型拟合误差解释排行榜？**

> 不同群体可能分别看重准确、速度、表达和成本，从而形成 A 胜 B、B 胜 C、C 胜 A 的多数偏好循环。单一潜在实力模型会把这些差异压缩为一个分数，可以通过经验两两胜率与拟合概率的偏差发现问题。按任务与用户群体分别拟合，报告样本量、评分区间和配对矩阵；选择模型时采用与目标业务相符的权重。对战覆盖不足也会影响估计，需要与循环偏好分开分析。

**6. (★★) 一个 Agent 的单次成功率为 60%。在独立尝试假设下，比较 $k=5$ 时的 Pass@k 与 Pass^k；再结合重试成本、结果选择和动作副作用，说明怎样设计实际评估。**

> 在每次成功概率均为 0.6 且相互独立的假设下，Pass@5 = 1 − 0.4⁵ = 98.976%，Pass^5 = 0.6⁵ = 7.776%。前者描述五次中至少一次成功，后者描述五次全部成功。实际重试还需要可用的结果验证或选择器，并计入失败尝试的时间和费用。对有外部副作用的任务，应设计隔离状态、幂等与恢复机制，在可控条件下测量每次失败及后果。k 取自实际允许的尝试预算或重复执行要求，并记录任务间差异与尝试相关性。

**7. (★★) 在有限预算下，怎样安排小规模诊断、配对比较、重复运行与保留集验证，使每一轮评估尽量帮助决策？**

> 先根据失败簇选择少量诊断任务，明确每轮要区分的原因假设；用配对条件比较单项变化，优先查看能解释行为的中间观测。筛出有价值的改动后增加任务覆盖与重复次数，估计差异区间。保留未参与调参的任务用于确认，涉及多方案筛选时处理多重比较。高风险边界与常见生产任务分别覆盖，避免将诊断集的集中采样当成总体分布。停止或扩大实验的条件应在运行前确定。

**8. (★) AndroidWorld 四项 Wi-Fi 任务中，完整元素树将成功率从 25% 提高到 100%，token 用量为原方案的 2.498 倍；精简后四项仍全部成功，token 为完整树的 0.506 倍。怎样设计裁剪规则与回归任务，保留控件状态、可访问性关系和后续操作依赖？**

> 保留可见文本、可操作与可聚焦控件、滚动区域、状态值和无障碍标签，以及解释这些元素所需的祖先链与邻接关系。将无语义容器折叠时，维持元素标识、位置、层级关系与状态的对应。裁剪前后比较同一组任务中的可操作元素覆盖、任务成功、输入 token 与延迟，并关注需要跨屏操作和状态验证的场景。先做目标子集诊断，再在独立应用与完整任务集回归；发现必要信息被删时恢复对应类型并加入测试。

**9. (★★) 用户模拟器按 Agent 提问逐步透露信息。怎样比较不同透露策略，并判断交互轮数、成功率和任务难度受到了什么影响？**

> 固定任务事实、初始环境和 Agent，分别配置主动完整透露、按问答逐步透露、允许遗漏或歧义等策略，比较需要的澄清次数、工具调用、成功率和错误类型。将真实用户轨迹中的透露行为作为校准依据，并分层覆盖熟练与不熟练用户。模拟器改变了信息取得的难度，既可能影响绝对分数，也可能影响模型排序；因此应在多个合理策略下观察结果，并给出对应的用户与任务条件。

## 第八章 模型后训练

**1. (★★) 一次定向微调改善了目标任务，却降低了通用工具调用能力。你会如何构造保留集、调整数据配比和训练量，并比较全参微调与 LoRA 的效果？**

> 先用相同任务和配置比较训练前后表现，区分目标能力、通用工具调用和其他关键能力。训练时混入原分布数据，根据留出结果选择配比、学习率与停止位置；也可加入参考策略约束或按任务挂载 adapter。LoRA 冻结基座，但挂载后的模型行为仍会改变，因此两种微调方式都要检查遗忘。VLM 等系统还可以按问题所在选择训练投影层、语言模型或视觉组件。

**2. (★★) 某项领域能力既可以通过参数训练学习，也可以用上下文示例和知识检索支持。你会依据哪些因素选择方案？**

> 先判断需求属于事实检索、可描述规则，还是感知与隐式决策模式。需要更新、引用、权限控制和删除的事实适合 RAG；少量规则与示例可以先放入上下文；稳定且反复使用的行为可以考虑参数训练。再比较调用规模、延迟、训练与维护成本。确定性的审批规则由程序执行，模型负责理解输入和处理规则之外的语言任务。

**3. (★★) 分别蒸馏直接回答的 Chat 模型、生成推理过程的 Reasoning 模型，以及多轮使用工具的 Agentic 模型，需要哪些训练材料和验证方法？**

> Chat 蒸馏需要有代表性的输入、可靠回答与任务质量检查，兼顾事实和表达。Reasoning 蒸馏需要可获取的推理示范，检查答案及关键中间步骤，并比较推理长度与质量。Agentic 蒸馏还需要工具定义、环境观测和状态变化，验证整条动作链；策略损失只覆盖模型生成位置，环境反馈作为上下文。学生容易进入示范之外的状态时，可以用在轨蒸馏补充这些前缀的监督。教师选择取决于质量和可用接口。

**4. (★★★) 客服 Agent 用 10 轮交互完成任务，最终获得成功奖励。你会如何把这一信号关联到中间决策？哪些步骤适合增加过程奖励？**

> 先保留完整任务的成功判据，再检查身份核验、必要信息获取和工具执行等中间事件是否可验证。PPO 可以利用价值估计构造各步优势；GRPO 可以比较同题的多条轨迹，必要时加入能够产生差异的路径信号。过程奖励应允许多种有效路径，并与结果奖励共同评估。对于难以可靠判断的中间步骤，可以保留终点反馈，再通过更多轨迹或教师监督改善信用分配。

**5. (★★★) 你有 10,000 美元预算提升客服 Agent 的表现。如何安排评估、上下文与知识、Prompt／Skills、程序约束和参数训练的投入？**

> 先用一部分预算建立代表性任务和错误分布，按失败频率、业务影响及修复成本排序。知识缺失优先改善检索，流程理解问题先试 Prompt／Skills，权限与金额约束用程序执行。剩余预算根据小规模试验分配给参数训练和部署评估。调用量、预期节省、维护频率与训练资源共同决定具体比例，还应预留回归验证与上线观察的费用。

**6. (★★★) 任务缺少明确奖励，环境交互又很昂贵。可以从哪些来源获得学习信号？你会如何验证这些信号确实改善了任务表现？**

> 可以从人工示范、偏好比较、教师逐 token 评价、环境中的可验证事件，以及模型生成的诊断中获得信号。模型模拟器能增加交互量，在轨蒸馏能增加每条轨迹的监督密度。验证时使用独立任务，同时记录任务质量、真实环境交互量和训练成本；对模型评价抽样校准，对模拟环境与部署环境的差异持续检查。

**7. (★★) 为每位用户或每家公司训练专属 LoRA，适合承载哪些个性化能力？哪些信息更适合保留在外部知识库中？**

> 长期稳定的表达风格、领域术语使用习惯和重复出现的决策模式，可以通过专属 adapter 学习。账户状态、频繁变化的产品事实、需要逐条引用或删除的记忆，更适合外部存储与检索。选择时还要考虑用户数据量、隔离、更新频率以及多 adapter 的部署成本。可以先用检索和上下文验证个性化收益，再把稳定行为迁入参数。

**8. (★★★) 结合 Weak-to-Strong Generalization 的研究思路，小模型能否为更强的 Agent 提供有用监督？请分别考虑局部验证、偏好标签和额外上下文，并设计检查监督偏差的方法。**

> 小模型可能擅长一个较窄的验证任务，也可能因为掌握规则、参考答案或额外材料而提供有用信号。强模型生成候选，小模型评价自己能够可靠判断的部分，再结合程序验证或人工抽查。可以用金标测量监督错误，按任务类型分析偏差，并检查强模型在独立评估中的表现。对分歧较大的样本降低权重或转交更可靠的评价来源。

**9. (★★) 一条轨迹的中间步骤大多正确却最终失败，另一条轨迹得到正确结果但违反了流程约束。如何结合过程和结果评价这两条轨迹？**

> 分别记录结果、过程正确性和硬性约束。第一条保留失败的结果标签，同时为可验证的有效步骤提供局部反馈；第二条记录结果达成，并对明确违规施加路径惩罚或按业务规则判定任务失败。评分权重应反映实际目标。对合法但未见过的动作序列，依据状态与结果验证，给探索新策略保留空间。

**10. (★★★) SWE-bench、τ²-bench 和 AndroidWorld 的环境与验证器可以用于训练。如何划分任务实例和模板，使训练材料得到利用，同时保留独立评估？**

> 共享环境接口与验证逻辑，分开训练和评估实例，并保存划分规则。参数化生成器可以产生同类新实例，用于检查分布内泛化；跨模板、跨业务或跨环境的留出任务用于检查更远的迁移。公开测试题一旦进入训练，就应从独立评估中移出。分别报告各类留出结果，可以判断收益来自实例适应还是更广泛的能力改善。

**11. (★★★) 目标任务的 pass@1 很低。怎样结合 pass@k、格式解析率、部分进展率和失败归因，决定采用 Mid-training、SFT 或 RL？**

> 先区分知识与基础能力不足、格式和协议错误，以及策略选择问题。pass@k 显示增加尝试后能否获得成功，解析率说明轨迹能否被执行和评分，部分进展率说明是否存在可用的中间信号。基础能力不足时补领域训练；已有能力但行为表达不稳定时用示范训练；能生成可评分且有奖励差异的轨迹时可以试 RL。切换依据是小规模试验中的质量收益、成本与保留集表现。

**12. (★★★) 一批 rollout 中只有少数超长响应尚未结束，其余任务已完成。如何提高训练集群利用率，同时控制异步采样带来的策略陈旧度？**

> 使用连续批处理和动态调度补入新请求，按长度分桶或分离采样与训练资源。异步流水线可以减少等待，同时记录行为策略版本与生成概率，限制允许的滞后并监控重要性比率。长度预算或柔性的超长惩罚可减少长尾，但需要区分无效重复与必要推理，并正确处理被截断的轨迹。最终比较吞吐、任务质量和训练稳定性。

**13. (★★★) 使用模型模拟搜索引擎或用户时，哪些模拟偏差可能误导 Agent？如何用任务状态和真实交互校准训练？**

> 模拟搜索可能过于容易返回相关材料，模拟用户可能总能理解含糊表达或对未兑现的承诺给出好评。这会减少模型练习查证、澄清和恢复的机会。评分尽量结合可验证的状态变化与交付物，另用人工样本检查语义质量。对有真实接口的工具，可以比较模拟与真实返回；对模拟用户，可以用真实对话中的行为分布和经授权的用户测试校准。发布评估同时覆盖离线任务和实际业务指标。

## 第九章 Agent 的持续进化

**1. (★★) 一条经验文档由三次成功轨迹和一次失败轨迹支持。失败发生在较新的 API 版本上。系统应如何判断这是经验被推翻，还是适用条件发生了变化？**

> 先按 API 版本、任务条件和环境状态对四条证据分层，而不是按数量投票。若旧策略只在旧版本成功、新版本稳定失败，应把经验的适用范围收窄并生成新版本候选；若在相同版本和前置条件下也失败，则应降低置信度或撤销。

**2. (★★) 客服 Agent 的用户满意度上升，但规则违规率也上升。为什么不能把满意度作为单一学习信号？你会怎样设计护栏指标？**

> 满意度可能奖励违规退款、泄露信息或过度承诺，因此它只能是质量指标，不能覆盖安全底线。护栏至少包括规则违规、隐私泄露、无证据陈述、承诺—行动不一致和越权操作；这些指标应设置不可被平均分抵消的硬阈值，再在合规候选中比较解决率、合规变通、简洁性和满意度。

**3. (★★★) 同一个“虚假承诺”问题可以通过 Prompt、Harness 检查或参数训练缓解。你会依据哪些证据选择修改位置？**

> 先定位根因。若模型知道工具未执行却仍使用完成式措辞，可用最小 Prompt 规则纠正；若承诺可以由回复文本与工具状态确定性比较，Harness 检查更可靠，也应作为高风险场景的最后防线；若问题横跨大量表达方式，反映的是广泛的语言—行动对齐能力，再考虑参数训练。应优先选择最小、最易验证和回滚的修改，同时在失败集与旧任务保留集上比较。

**4. (★★★) Agent 能修改工具和验证器，却不应修改批准自身更新的可信根。你会如何划分这两部分的权限和代码边界？**

> 把可进化的代码放在低权限的沙盒中，只允许它生成补丁和测试；权限系统、API key、发布控制配置和更新验证器属于安全机制，沙盒内的 Agent 无读写权限。Agent 生成的代码修改必须由安全机制在隔离环境中复现、回归后才能发布。

**5. (★★) 经验知识库不断增长后，检索错误和知识冲突会抵消学习收益。如何设计版本、时效和淘汰机制？**

> 每条经验保存来源轨迹、适用条件、环境版本、验证时间和置信度；冲突条目不要静默覆盖，而应按条件分支或标记。周期性“睡眠学习”合并重复条目。

**6. (★★★) 参数学习擅长自然语言风格，却难以保证硬性业务规则。请为医疗客服设计一套参数、知识、Skill 和代码约束协同的持续进化方案。**

> 参数（后训练模型）负责医学语言理解、自然且有同理心的表达和复杂意图识别；知识库保存最新版指南、药品说明与机构政策，并要求回答引用来源；Skill 描述问诊信息收集、风险分级、转人工和随访流程；服务端代码强制身份验证、隐私最小化、禁忌校验、紧急风险升级和权限边界。生产轨迹先按医疗安全、事实可靠性、承诺—行动一致性和表达质量评价，再分别生成四类候选更新；任何参数或流程改动都必须通过医疗安全保留集与人工复核后灰度发布。

**7. (★★★) 历史回放中的某个探索策略在所有旧发现树上得分最高，却在下一轮在线探索中退化。哪些支持域偏差、随机性和评价过拟合可能造成这种结果？你会怎样划分回放世界并设计发布门槛？**

> 旧发现树只覆盖旧策略访问过的状态和分支，无法证明新策略在未探索区域也有效；在线任务、工具或环境的变化还会造成分布偏移。随机种子、模型采样和工具噪声可能改变排名，反复在同一批树上挑选策略也会对评估集过拟合。应按任务族、时间和独立发现树划分开发集、验证集与封存测试集，同一棵树及其衍生轨迹不可跨集合泄漏。固定模型、工具版本与计算预算，使用多个种子与基线配对比较，报告收益、不确定性、成本和违规率。预先设定质量改进及安全、成本门槛；离线通过后再做小规模在线对照，只有在线收益得到支持且护栏无退化才逐步发布，并保留回滚条件。

## 第十章 多 Agent 协作

**1. (★★) 共享上下文的多 Agent 协作中，后续 Agent 继承了前序 Agent 的完整上下文。但前一个 Agent 积累的“思维惯性”可能影响后续 Agent 的判断——比如继承了“需求分析师”上下文的“代码审查员”，可能还是倾向于从需求角度思考而非代码质量角度。如何检测和消除这种角色间的干扰？**

> 检测：用 LLM 分析 Agent 轨迹，判断新角色是否仍有“代入”旧角色的行为。消除：切换阶段时同时更换系统提示词与工具集（移除提问工具、换上 linter/测试工具），强化新身份。在上下文末尾添加系统状态栏，突出当前角色信息。如果实在无法消除角色干扰，应考虑改用不共享上下文的协作方式。

**2. (★★) 管理者模式中，Manager Agent 负责任务分解和结果整合。但 Manager 本身的能力上限决定了整个系统的能力上限——如果 Manager 无法正确分解任务，子 Agent 再强也无用。如何确保 Manager 的分解质量？**

> 依据 Plan-and-Act 的结论，“弱规划者是系统瓶颈”，应把最强模型分配给 Manager。Harness 手段：分解结果先经审核 LLM 交叉验证，再交付执行；要求 Manager 在分解任务时，为子任务定义明确的验收标准与依赖关系。

**3. (★★) 去中心化模式借鉴了人类组织的最佳实践。但人类组织也有大量失败模式——沟通不畅、责任推诿、目标冲突。你认为 Agent 社会中最可能出现哪些“组织病”？如何预防？**

> 对照 MAST 的三大类问题：接口不清、职责重叠；对目标的理解不一致、信息被下游误解；谎称“已完成”。此外，还有错误级联放大（传话游戏）、角色间循环移交、Agent 群聊不断发散而无法收敛等问题。预防措施包括：使用契约式接口与统一的消息信封、采用任务状态机并进行验收验证、从独立视角进行交叉验证、检测角色间的相互推诿等。

**4. (★★★) 在管理者模式中，当多个子 Agent 并行执行时，一个子 Agent 的发现可能使其他子 Agent 的工作变得毫无意义（比如搜索任务中一个 Agent 已经找到了答案）。设计一种高效的级联终止机制，实现“一个成功，全员停止”。**

> 子 Agent 发 `target_found` 给管理者，随后广播 `terminate`；每个子 Agent 在 ReAct 循环安全点定期检查终止信号，优雅清理（关浏览器会话、释放锁、写完文件）后结束。

**5. (★★★) 本章介绍的乐观锁机制解决了单文件的并发写入冲突，但实际的多 Agent 系统中，共享文件系统还面临跨文件的语义冲突、命名空间污染（Agent 随意创建文件导致目录混乱）和单点故障（一个 Agent 错误地删除了所有文件）等问题。你会如何设计更完善的文件系统治理机制？**

> 分区治理：按照表10-3 划分四类区域，用私有 scratchpad 隔离试错过程。语义冲突：由编排层约定目录级锁文件，检查并获取目录锁之后再进行修改。命名空间污染：制定目录规范和命名约定。单点故障：采用版本控制系统，确保可以利用版本历史回滚，并尽量缩小权限范围。

**6. (★★★) 基于市场机制的 Agent 协作（Pinchwork、RentAHuman）引入了交易关系：一个 Agent 花钱雇佣另一个 Agent（或人类）完成任务。那么，雇主 Agent 如何自动衡量执行者交付的结果质量？如果执行者声称已完成但雇主认为质量不达标，争议由谁仲裁？如何防止劣币驱逐良币？**

> 验收不能只是读取 Agent 轨迹，而要采用确定性的外部验证，如执行测试、渲染截图、调用工具核验；利用生成与验证之间的难度差异降低验收成本。争议由独立的第三方审核 Agent 仲裁，并配合资金托管。为防止劣币驱逐良币，应建立基于历史交付记录的声誉体系，让价格信号与质量挂钩。

**7. (★★) RentAHuman 让 Agent 通过加密货币雇佣人类，反转了传统的人机关系。如果这种模式普及，人类在 Agent 经济中扮演什么角色？仅仅是执行 Agent 无法完成的物理任务吗？**

> 不只是执行 Agent 无法完成的物理任务。人类还可以提供 Agent 单独推理时无法获得的新信息，包括现场感知与真实世界反馈；充当最终验收者与争议仲裁者；作为法律与责任主体承担授权和问责；设定目标、作出价值判断，并在信息不对称和道德边界处发挥制衡作用。

**8. (★★) 人类社会需要多人分工协作，是因为每个人的能力有限——做前端的不一定懂后端，懂设计的不一定会运维。但大模型更像一个“全才”。相关研究表明，在纯文本推理任务上，多 Agent 辩论在等量计算资源下并不优于单 Agent。那么，使用多个 Agent 而非单个 Agent 的真正优势到底在哪里？**

> 1. 引入外部反馈：执行结果、视觉截图等可以带来生成时不存在的新信息。
> 2. 使用目标与角色设定各异的多个 Agent，让它们像人类社会成员一样互相讨论、博弈，可以避免单一 Agent 陷入思维误区。
> 3. 多 Agent 的上下文隔离可以突破上下文窗口限制，实现超长工具调用链。

**9. (★★★) 本章将“共享上下文”与“不共享上下文”作为多 Agent 系统的核心设计维度。共享上下文让所有 Agent 看到相同信息，似乎更利于协调。但《三体》中的三体人思维完全透明，技术发展却陷入停滞；回形针思想实验也表明，当群体趋向同一目标时，多样性随之丧失。在多 Agent 系统中，如何在效率与多样性之间找到平衡？**

> 完全共享会放大思维惯性与错误级联，隔离才有认知多样性。手段：用不同提示词/模型制造思维偏好（brainstorm、debate）；交叉验证者不看前序思考过程只看原始证据。

**10. (★★★) 给一个 Coding Agent 分配 30 步预算和 300 步预算，它的工作策略应该如何不同？研究表明，单纯增加步骤预算并不能保证性能提升——Agent 会在浅层搜索后过早“饱和”。设计一种“预算感知”机制，让 Agent 在小预算下快速实现核心功能，在大预算下增加规划、测试和审查环节，充分利用额外的计算资源。**

> 机制：每一步都向提示词注入总预算与剩余预算，按照剩余预算的比例动态调整探索与利用的权重。例如，小预算（30 步）下，跳过规划和审查，直接实现核心功能并进行基本验证；大预算（300 步）下，先规划、再实现、再测试、再审查改进，并按里程碑设置检查点以评估进展，防止浅层饱和。

**11. (★★) 本章对比了多 Agent 系统与操作系统。虚拟内存与分页、文件权限、死锁检测、调度算法，各对应 Agent 世界的什么？又有哪些操作系统概念在 Agent 世界找不到对应物，为什么？**

> 可能的延伸：虚拟内存/换页 ↔ 上下文压缩与检索（热信息留在窗口内，冷信息换出到文件与记忆库，用时再取）；文件权限 ↔ 工具白名单、只读挂载、凭证边界；死锁检测 ↔ 循环移交与互相等待的检测（移交次数上限、超时）；调度算法 ↔ 异步事件处理（第四章）。找不到对应物的地方源于强制力不同：进程的指令由硬件强制执行，Agent 对提示词只是大概率遵循。
