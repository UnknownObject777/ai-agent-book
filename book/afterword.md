# 后记：回到 Agent = LLM + 上下文 + 工具 {.unnumbered}

本书从一个公式开始：**Agent = LLM + 上下文 + 工具**。读完十章，再看这三个要素，我们已经能把它们放进一个实际运行的系统：模型理解任务、作出决策，上下文提供当前所需的信息，工具获取观测并执行行动。

第一章用这套功能分解建立全局认识，再用 **Agent = Model + Harness** 说明生产实现中的分工：模型负责决策，Harness 组织上下文、工具接口、运行循环和状态，实施约束、验证与纠正。后续章节沿着构建、评估与进化、协作三条主线展开。

- **构建 Agent（第二至六章）。** 上下文工程组织一次决策所需的信息，记忆与知识库支持跨会话保存和检索。工具提供观测与动作接口，代码生成让 Agent 能够编写新的工具和系统。交互一章进一步把这些接口扩展到语音、图形界面和物理世界，并讨论持续接收事件的运行方式。
- **评估与进化（第七至九章）。** 评估将表现转化为可比较的反馈，后训练通过数据与环境更新模型参数，持续进化则把运行经验转化为知识、指令、程序或参数的更新，并用验证和发布流程管理变化。
- **协作（第十章）。** 多 Agent 系统通过分工、通信和相互检查，重新组织上下文、工具与责任。成员数量增加后，还需要管理共享状态、任务依赖、资源和争议。

这些方法在同一个系统中相互配合。第九章的持续进化就是一个汇合点：轨迹与知识系统保存经验，代码能力支持修改工具与 Harness，评估判断改动是否有效，版本与恢复机制帮助系统稳步更新。前面的构建方法，由此延伸为长期改进的方法。

## 两朵乌云 {.unnumbered}

1900 年，开尔文用“两朵乌云”描述热与光的动力学理论面临的难题，其中涉及以太运动与能量均分。[^kelvin] 借用这个比喻，我也看到 Agent 发展中的两朵乌云：实时交互，以及从交互中持续学习。

**第一朵乌云，是 Agent 如何流式地、实时地与环境交互。** 常见的请求—应答流程由用户先提出要求，Agent 再思考、执行和回复。真实环境却持续变化：用户会插话，页面会更新，新的邮件和通知随时到达。我期待的 Agent 能边听边规划、边执行边接收变化，也能根据用户设定的目标主动发现待办事项，例如识别一封需要及时处理的邮件。

走向实时交互，可以同时推进两条路线。

一条是**在架构上分离快慢路径**。前台快速处理语音轮次、打断和短反馈，后台承担检索、规划和较长时间的推理。两条路径通过事件与状态协调：新信息到达后，系统判断是否继续当前任务、更新计划或取消已经失效的操作。第六章的语音和异步事件架构讨论了这组机制。

另一条是**加快模型推理**。生成速度提高，可以缩短同一段推理的耗时，也让系统有机会在相同时间内比较更多候选。小米 MiMo 报告，通过 FP4 量化、DFlash 推测解码与 TileRT 推理系统的协同优化，在单个通用 8 卡节点上实现了万亿参数模型超过 1000 token/s 的生成速度。[^mimo] Taalas HC1 则采用模型专用芯片，在 Llama 3.1 8B 上报告了约 17000 token/s 的单用户生成速度。[^taalas] 两个例子分别展示了通用硬件上的系统优化，以及针对特定模型的硬件专用化。

更快的生成让等待缩短，持续输入和事件调度让系统及时接收变化，取消与状态同步让执行跟上新的决定。评估实时体验时，可以沿着“输入到达—模型决策—工具执行—反馈返回”测量整条链路，再确定最需要优化的环节。

**第二朵乌云，是 Agent 如何从成功与失败中持续积累经验。** 预训练赋予模型广泛知识，运行中的每次任务又会产生新的结果：哪些步骤有效，哪个工具容易出错，用户接受了怎样的表达。把这些经历保存下来，并让它们改善下一次行动，是第三章与第九章贯穿讨论的问题。

我用“小世界”和“大世界”概括两种看待学习需求的思路。

**“小世界假设”**强调通用知识可以被一个足够大的模型吸收。沿着这个方向，几万亿参数的模型可能容纳极其广泛的知识和方法，主要挑战是获得高质量训练数据。编程提供了一个有启发的例子：大量公开代码、文档和可执行测试，为模型学习与结果检验创造了条件。行业合作则可以把专业任务和经验引入训练，让更多领域的能力进入基础模型。

**“大世界假设”**强调具体情境的丰富性与变化。某家公司的代码规范、某位用户喜欢的 PPT 风格、某个客户的沟通习惯，都需要在实际交互中了解；组织流程和偏好还会继续变化。系统因此要持续维护记忆、知识和操作方法，再根据反馈调整行为。经验可以先写成知识文档、指令或程序，经过筛选和验证后，也可以用于更新模型参数。

递归自我改进（RSI）与 AI for Science 进一步把这一问题推向探索前沿。Agent 提出假设，执行实验，根据结果修订，再积累可复用的方法。这里的学习既包括吸收已有知识，也包括通过探索获得新知识。我认为，持续学习与适应将成为 Agent 最重要的能力之一。

实时交互带来更密集的反馈，持续学习让反馈改善后续决策。这两条路线需要模型能力、运行架构和评估方法共同进步，也把我们带到本书的另一个核心判断：模型与 Agent 系统相互推动、共同演进。

## 模型与 Agent 的共同演进 {.unnumbered}

多级上下文压缩、失败重试、结果验证和访问控制，都是工程师在真实任务中逐步建立的机制。每项机制背后都有具体问题：信息超过输入容量，工具返回异常，模型遗漏完成条件，或者一次操作需要特定权限。分析这些过程，可以发现模型和系统各自需要改进的地方。

真实业务由此形成一条反馈循环：用户提出任务，Agent 在环境中执行，评估识别失败原因，工程师改进 Harness，经过整理的轨迹与反馈再进入模型训练。下一代模型上线后，团队重新评估系统，调整分工与实现。这条循环把业务问题、工程方法和模型能力连接起来。

第一章提出过一个问题：**模型会不会最终吃掉 Harness？** 我的判断是，模型会逐步吸收一部分原先由外部编排实现的能力，Harness 的工作也会随之变化。第六章的交互模型就是一个例子：模型直接学习轮次判断、插话和语音响应后，系统可以简化相应的启发式规则；音频传输、执行取消与状态管理继续由运行时承担。

模型升级后，可以通过对照评估逐项简化已有机制，同时保留系统必须执行的职责。业务权限由可信身份和授权规则决定，预算由运行时与服务配额执行，外部操作由工具和环境完成。新的任务又会提出更复杂的要求，促使团队设计新的上下文组织、验证和恢复方法。**模型吸收已有方法，工程继续解决新的问题。**

这也是我理解《苦涩的教训》的一种方式：充分利用计算与学习带来的通用能力，同时通过工程把这些能力接入真实任务。模型训练、部署和业务迭代有各自的节奏，Harness 让系统能够及时处理当前需求，并把有价值的反馈保存下来。

模型与产品由同一团队持续打磨时，这条反馈链可以更紧密。以 Anthropic 的 Claude Code 为例，模型能力影响工具与上下文设计，真实使用中的问题又能为后续模型和系统改进提供方向。第一章介绍的 LangChain 案例展示了系统工程的直接收益：固定使用 GPT-5.2-Codex，调整 Harness 后，Terminal Bench 2.0 得分从 52.8% 提高到 66.5%。完成前自检、重复操作检测和预算分配，都来自对失败过程的具体分析。

我认为，真实业务、反馈数据和迭代能力越紧密，团队就越容易形成持久的竞争力。对模型团队而言，应让有价值的任务与反馈尽快进入数据、训练和评估流程。对应用团队而言，Harness 帮助产品达到当前的业务要求，长期积累则来自对用户需求的理解、独特的数据、稳定的渠道、用户信任、网络效应，以及人与 Agent 共同完成的现实工作。持续改进系统，也是在积累这些能力。

模型、API 和产品会继续变化，“当前需要什么信息”“允许采取哪些行动”“怎样验证结果”仍会贯穿系统设计。理解这三个问题，就能判断新能力适合放在什么位置，哪些组件可以简化，哪些环节需要补强。工程实践产生方法，评估检验方法，反复验证与抽象让方法沉淀为可复用的原则。

本书希望把这样的判断力交给你：从具体任务出发，理解 Agent 的结构，构建能够运行的系统，再根据反馈持续改进。正文、配图与配套实验代码都已开源，欢迎亲手运行实验、尝试新的方案，并通过 issue 和 PR 分享发现。Agent 能通过代码创造工具、扩展能力，也让我们拥有了更多实现想法的方式。
